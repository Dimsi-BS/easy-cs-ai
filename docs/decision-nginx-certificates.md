# Decision: TLS certificates of the reverse proxy

[← Back to docs](README.md)

**Status:** accepted, the three strategies are implemented (unit-tested, not yet run on a VM)

## Context

The [nginx](../search/nginx.md) reverse proxy provides HTTPS and the API key in front of the inference engines. It needs a certificate, and the machines are VMs provisioned unattended (cloud-init), where nobody can answer a prompt and where the network is sometimes restricted (see the mirror URL in [decision: VM script generator](decision-vm-generator.md)).

What is known about the deployments: either **the customer supplies an SSL certificate**, or the machine gets one from **Let's Encrypt**. The first strategy, self-signed, stays as the default for everything that has neither.

The state records the strategy as `listen.tls` (see [state format](spec-state-format.md)): `self-signed`, `provided` or `letsencrypt`.

## Options

| Option | Needs | Pros | Cons |
| --- | --- | --- | --- |
| `self-signed` | nothing | Works everywhere, offline, zero-conf | Clients must trust it or disable verification; browsers warn, which hurts the chat interface |
| `provided` | a certificate and its key from the administrator | Fits an internal CA, a wildcard or a purchased certificate; no network | The key is a secret that has to reach the VM (see [secrets](spec-script-contract.md#secrets)); renewal is the customer's job |
| `letsencrypt` | a public domain pointing to the VM, port 80 reachable from the Internet | Trusted by every client; renewal by `certbot` | Fails on private networks; rate limits when a fleet of VMs is rebuilt; the subscriber agreement must be accepted |

## Decision

One parameter, `--tls self-signed|provided|letsencrypt`, in the `describe` of the proxy so that `apply` and the generator validate it. **Default: `self-signed`**, so `install --defaults` always converges. Switching is a re-run of `install` (idempotence rules of the [contract](spec-script-contract.md#idempotence)). Options that belong to another strategy are a usage error (exit 2), never ignored.

### `self-signed`

Generated by the script with `openssl` (EC P-256, 10 years), valid for the `server-name` (default: the hostname), `localhost` and `127.0.0.1`. Regenerated only when the name changes or when a certificate left by another strategy is replaced.

### `provided`

- `--tls-cert <path>`: the certificate, PEM, the full chain first.
- `--tls-key-file <path>`: its private key, PEM, mode `0600` or stricter, `-` for stdin, or `EASY_CS_AI_NGINX_TLS_KEY` with the PEM text. The key follows the secret rules (never on the command line, never printed, never in the state), and is declared `secret` in `describe`, so the configuration file names its source (`file`, `env`) as for any secret.
- Both are copied into `/etc/easy-cs-ai/nginx/server.crt` and `/etc/easy-cs-ai/secrets/nginx.tls-key`, so a later re-run needs neither: **`install --tls provided` without `--tls-cert` keeps the installed certificate**. A new pair given the same way replaces it, which is how the customer renews.
- Checked before anything is written (exit 2): the certificate is a valid PEM and **not expired**, the key is readable and **belongs to the certificate** (public keys compared), the key is **not encrypted** (nothing could type the passphrase). Only warnings: the certificate expires in less than 30 days, or does not cover the server name.
- Renewal and the reload of nginx are the customer's business: nothing in the project watches the expiry date after the install.

### `letsencrypt`

- Mandatory: an **explicit `--server-name`** (a public domain name, not an IP address, not `localhost`: the hostname default is not used for this), and **`--tls-accept-terms`** (or `EASY_CS_AI_NGINX_TLS_ACCEPT_TERMS=true`). The subscriber agreement is the administrator's to accept: the script never accepts it by default.
- Optional: `--tls-email <address>` for the expiry notices; without it the account is registered without an address.
- Challenge: **HTTP-01 on port 80**. The script adds a small `server` on port 80 (`conf.d/easy-cs-ai-acme.conf`) that serves `/.well-known/acme-challenge/` from `/var/www/easy-cs-ai-acme` and redirects the rest to HTTPS, reloads nginx, then runs `certbot certonly --webroot` (package `certbot`, no nginx plugin, which would edit the configuration). The certificate stays in certbot's own directory and nginx points to `/etc/letsencrypt/live/<name>/`.
- Renewal: certbot's own timer, with a deploy hook that reloads nginx. Nothing else of the project is involved.
- Preflight: port 80 must be free, or held by nginx itself (the distribution's default site).
- **No silent downgrade**: a refused or unreachable ACME server is exit 5 with a hint, never a self-signed certificate behind the administrator's back. An existing certificate for the name is reused, not requested again (rate limits).
- `uninstall` removes the challenge server and the webroot but **keeps the certificate**, like any user data; `--purge` deletes it with `certbot delete`.

### Health check

The proxy is proved by 401 without the key and 200 with it, requested on the loopback:

| Strategy | Request | Why |
| --- | --- | --- |
| `self-signed` | the certificate pinned with `--cacert` | verified, no trust store needed |
| `letsencrypt` | by the server name (`--resolve` to the loopback), system trust store | verified like a real client |
| `provided` | verification off, **plus** a comparison of the certificate that nginx serves with the file (SHA-256 fingerprint, `openssl s_client`) | the customer's CA may be unknown to the VM, but the check still proves nginx serves that very certificate |

## Consequences

- With `self-signed`, the chat interface and the clients must trust the certificate; the script records its path in the state (`listen.certificate`) so a client can be set up, and a browser warns until it does.
- The state `params` hold `tls` (and `tls-email`), never a key; `secrets` lists the paths of the API key and, except for Let's Encrypt, of the TLS key.
- Moving from a strategy to another is one `install` with the new options; the files of the previous one are replaced (or, for the challenge server, removed).

## Open questions

- Only HTTP-01 is implemented. A DNS-01 challenge (private network with a public name, wildcard) is not, and no DNS provider plugin is planned.
- The challenge server listens on IPv4 only (`listen 80;`), since a `[::]` listener fails on a machine without IPv6; a domain with an AAAA record would need it.
- Whether the certificate is shared with the chat interface when it is served by the same proxy.
- Reading the expiry date of a `provided` certificate to warn in `status`.

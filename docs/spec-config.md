# Spec: configuration file and `apply`

[← Back to docs](README.md)

**Status:** accepted (secrets handling still open, see [open questions](#open-questions))

## Purpose

One declarative **configuration file** describes a deployment: which components, with which options, and which models. It has two uses, with one format:

- `easy-cs-ai apply <file>` (layer 2) interprets it and makes the machine match it;
- the [generator](spec-vm-generator.md) writes it at the end of an interactive session (`--config-only`) and reads it back with `--config` to generate a script without prompting (regeneration, tests).

For the VM post-install layer, the generated script embeds the configuration (the slice of its VM when the file names several, see [Several VMs](#several-vms)) and hands it to `apply`, so the configuration travels **inside the generated script**: no external input file (see [spec: VM script generator](spec-vm-generator.md#generated-script)). The package itself is downloaded from a pinned source, not embedded, see [decision: VM script generator](decision-vm-generator.md).

`apply` builds on the [script contract](spec-script-contract.md) and the [CLI spec](spec-cli.md); it adds no capability the CLI does not have, it lets one file drive `install` and `add`.

## Format

JSON, like every other structured file of the project: `jq` is already a dependency (see [scripting language](decision-scripting-language.md)), whereas YAML would need `yq`.

```json
{
  "schema_version": 1,
  "components": [
    { "type": "provisioning", "name": "llmfit" },
    { "type": "proxy", "name": "nginx", "options": { "server-name": "ai.example.org" } },
    { "type": "engine", "name": "ollama", "default": true, "options": { "port": 11434 } },
    { "type": "chat-interface", "name": "librechat", "default": true }
  ],
  "models": [
    { "name": "llama3.2:3b", "engine": "ollama", "chat_interface": "librechat" }
  ]
}
```

### `components`

| Field | Required | Meaning |
| --- | --- | --- |
| `type` | yes | One of the contract types (`engine`, `chat-interface`, `proxy`, `provisioning`) |
| `name` | yes | Component name, as shipped (`<type>/<name>.sh`) |
| `default` | no | Make it the default of its type, forwarded as `--default` (see [state format](spec-state-format.md#defaults)) |
| `options` | no | Options of the script, keyed by option name **without** `--` (the `describe.options[].name`). Values are strings, numbers or booleans |
| `vm` | no | The VM this component belongs to, when the file describes several, see [Several VMs](#several-vms). Absent on every component of a one-VM file |

- An option left out takes the script's built-in default, as on the command line.
- At most one entry per component (per VM, see [Several VMs](#several-vms)). Several of one type are allowed (e.g. two engines); `default` is set on at most one per type (and per VM).
- Order in the file carries no meaning: the install order comes from `requires`.

### Secrets

An option flagged `secret` in `describe` is never given as a plain string. It is an object naming its source, the same channels as the [contract](spec-script-contract.md#secrets):

| Form | Source |
| --- | --- |
| `{ "file": "/path" }` | `--<name>-file`, the file must be mode `0600` or stricter |
| `{ "env": "NAME" }` | The environment variable of the process running `apply` |
| `{ "generate": true }` | Generated by the script (the contract default when the option is absent) |

Whether a literal secret may appear in the file is an [open question](#open-questions).

### `models`

| Field | Required | Meaning |
| --- | --- | --- |
| `name` | yes | Model name, as the engine knows it |
| `engine` | no | Engine name, listed in `components` or already installed. Default: the only engine in `components`, else the one with `default: true`, else a validation error. With several VMs, see [Where a model goes](#where-a-model-goes) |
| `vm` | no | The VM the model is installed on, when the file describes several: with `engine`, the **place** of the model, see [Where a model goes](#where-a-model-goes). Absent in a one-VM file |
| `chat_interface` | no | Chat interface name (listed in `components` or already installed), or `null` for none. Default: like `engine`, and none if the file lists no chat interface. With several VMs, the chat interface of the engine's VM, else none ([Several VMs](#several-vms)) |
| `force` | no | `true` skips the llmfit fit check, as `add --force` does |

### Several VMs

A component may carry `vm`, the name of the VM it belongs to, so that one file describes a deployment spread over several machines (see [spec: two VMs](spec-two-vm.md)). A file with no `vm` is a one-VM file and behaves exactly as described everywhere else in this spec.

- **Shape**: a string of lowercase letters, digits and dashes, starting with a letter (`engine`, `web`). Another type is `wrong_type`, another form `invalid_value`.
- **All or none**: when one component has `vm`, every component must, otherwise the first one without it is the error `missing_vm`.
- **One entry per component and per VM**: `nginx` may be listed once on each VM with its own options (server name, certificate), the same component twice on one VM is `duplicate_component`, and `default` is set on at most one component of a type **on a VM** (`several_defaults`).
- **Slices**: the file is cut by `vm`, in the order each VM first appears. A slice is an ordinary one-VM configuration (the components of that VM, without `vm`, and the models of its engines), and is validated **exactly as a one-VM file**: order from `requires`, a requirement satisfied by a component of the same VM only (what another VM has is not on this machine), options, secrets. Errors and warnings keep the paths of the file as written, and name the `vm` they are about.
- **Models** have a place, see [Where a model goes](#where-a-model-goes). A model is linked only to a chat interface **of its own VM** (the default of `chat_interface` is the one of that VM, and none when it has none); an explicit `chat_interface` that exists only on another VM is the error `chat_interface_other_vm`: a link between two machines is made by hand, see [spec: two VMs](spec-two-vm.md#next-steps).
- **What a VM receives**: the generator embeds the slice in the script of its VM (see [spec: VM script generator](spec-vm-generator.md#generated-script)), with no `vm`, so `apply` on the VM reads a plain one-VM file and knows nothing of the others.
- **`apply` on a file with `vm`** is refused (exit 2, listing the VM names) unless `--vm <name>` selects a slice, which is then applied as a one-VM file. `--vm` on a file with no `vm`, or with an unknown name, is exit 2. Pruning, `--dry-run` and the plan concern that slice only.

#### Where a model goes

A model is installed on **one engine of one VM**. That pair, the **place** of the model, is what the file attaches a model to: `vm` and `engine` of the entry. An engine component is identified by its name within its VM (the same component twice on one VM is refused), so the pair names exactly one component, and the same engine on two VMs is two places.

A file whose components have no `vm` is a one-VM file: the model resolves as in the table above, and a `vm` on a model is the error `unknown_vm` (the file names no VM). In a file that names several VMs, `vm` and `engine` resolve as follows, and the first row that applies decides:

| `vm` | `engine` | Place |
| --- | --- | --- |
| given | given | The engine of that name on that VM. Not on it, but on another VM: `engine_other_vm`. Nowhere: `unresolved_engine` |
| given | absent | The engine of that VM: the only one, else the one with `default: true` on that VM, else `ambiguous_engine`. None on it: `unresolved_engine` |
| absent | given | The VM that has an engine of that name: exactly one, else `ambiguous_engine` (the message asks for `vm`). None: `unresolved_engine` |
| absent | absent | The only engine of the file, else `ambiguous_engine` naming the candidates as `<vm>/<engine>` |

- A `vm` that no component has is `unknown_vm`, with the VM names of the file in the message.
- The same model may go on several places (the same name on two engine VMs is two entries). The same name twice on the **same place** is `duplicate_model`, in a file that names several VMs only: a one-VM file is validated as it is today.
- The resolved place goes into the plan of `config validate` (each model carries its `vm` and `engine` as resolved, see [spec: capabilities](spec-capabilities.md#config-validate)), and into the slice: a model goes to the slice of its VM, **without `vm` and with `engine` filled in** when it was absent, so that the slice resolves the model exactly as written, whatever the other VMs hold.
- **The session and a program that follows the [journey](spec-journey.md) write both fields on every model** when the file names several VMs, so that the file says where each model goes. A file written by hand may leave them out where the table gives one answer.
- The place decides everything that follows: the VM where the model is pulled and sized (`plan` is called per VM with its models, see [spec: model fit](spec-model-fit.md#declared-resources)), the engine that serves it, the proxy of its VM that fronts it, and the [next steps](spec-two-vm.md#next-steps) that read its URL.

#### Compatibility of the `vm` field

`schema_version` stays 1: `vm` is an optional field and a one-VM file is unchanged. The validation is **strict**, an unknown key is refused (unlike the state and `describe`, whose readers ignore what they do not know), so a CLI older than this field refuses a file that uses it with `unknown_key` at `$.components[<n>].vm` or `$.models[<n>].vm`, exit 2, and not with `unsupported_schema_version`. That refusal is the right one, since ignoring `vm` would install the components of every VM on one machine; only its wording is less clear than a version error. The VMs themselves are not concerned: a generated script pins its package version and embeds a slice without `vm`, which any version reads, including an older `--package-version`. A bump to 2 when `vm` is present would give the clearer message; it is left for later, see [open questions](#open-questions).

### Validation

`apply` and the generator validate the file **before any side effect**, against the `describe` of the shipped scripts: unknown top-level key, unknown type, name or option, wrong value type, `schema_version` higher than supported, a secret given as a plain string, an unresolvable `engine` / `chat_interface` of a model. Each problem is reported with its JSON path on stderr, and the exit code is 2. A higher `schema_version` is refused, never guessed. For a file that names several VMs, each slice is validated as a one-VM file, and `missing_vm`, `chat_interface_other_vm`, `unknown_vm`, `engine_other_vm` and `duplicate_model` join the codes (see [Several VMs](#several-vms) and [Where a model goes](#where-a-model-goes)).

## `apply`

```text
easy-cs-ai apply <file|-> [--vm <name>] [--prune] [--dry-run]
```

`--vm <name>` selects one VM of a file that names several, see [Several VMs](#several-vms). `-` reads the configuration from stdin. Requires root (exit 4), except with `--dry-run`. The CLI never prompts, as for the other commands.

### Semantics: converge

`apply` makes the machine **reach** what the file says, and is safe to run again. Like `install --defaults`, it converges.

- **Nothing is added that the file does not name.** There is no `--defaults` here: the file is the explicit choice. A component required by another (`requires`) that is neither listed nor already installed is an error (exit 4, naming the command that would fix it), as for `install` without `--defaults`. See [Dependencies](spec-cli.md#dependencies).
- **Nothing is removed by default.** A component or a model present on the machine but absent from the file is left alone. `--prune` is the explicit opt-in (see below).
- A listed component already installed with the same options is a no-op, and with different options it is reconfigured: this is the script's own [idempotence](spec-script-contract.md#idempotence), the CLI does not compare anything itself.

### Steps

1. **Read and validate** (no side effect). With `--vm`, the file is cut into its slices first and only the selected one goes on, as a one-VM file. `--dry-run` prints the plan after this step and exits 0.
2. **Order** the components from `requires` (from `describe`, not hardcoded), the same computation as the default stack of [`install`](spec-cli.md#install).
3. **Components**: for each, in that order, the CLI runs the equivalent of `install <type> <name>` with the options of the entry (and `--default` when set). Secrets are passed through their channel, never on the command line.
4. **Models**: for each, the equivalent of [`add`](spec-cli.md#add) with the resolved `engine` and `chat_interface` (`--no-chat-interface` when `null`, `--force` when set), including the fit check, the wiring and its rollback.
5. **Prune** (only with `--prune`): after everything else succeeded, in reverse order, `remove` for each installed model absent from the file (of the engines listed), then `uninstall` for each component absent from the file, without `--purge`.

### Failure and resume

- The run stops at the first failing step and returns its exit code, naming the step (`[ERROR] apply: install engine ollama failed (exit 5: …)`).
- **No global rollback.** Installed components are kept: they are what the file asked for, and a second `apply` resumes with what is left. A failing `add` is rolled back as specified for `add` (and exits 7 if that rollback is incomplete).
- `--prune` runs last, so a failed run never removes anything.
- Interruption (SIGINT, SIGTERM) behaves as for `add`: the running script finishes its own cleanup, then the command ends with 130 / 143.

### Journal

`apply` writes `apply start components=<n> models=<n> prune=<bool>` (plus `vm=<name>` with `--vm`) and `apply end exit=… duration=…` through `log_event`, around the lines of each step (see [Action journal](spec-script-contract.md#action-journal)). The file's content is not logged, only counts.

## Relation to the other commands

| Need | Command |
| --- | --- |
| One component, by hand | `install <type> <name>` |
| The rank 1 stack | `install --defaults` |
| One model on the current setup | `add <model>` |
| A described deployment, reproducible | `apply <file>` |

`apply` is the form used by the generated VM script. `install --defaults` stays for the quick, undescribed case.

## Implementation notes

- Validation is one `jq` program run over the file and the `describe` of every listed component, so the whole list of problems comes out at once, each with its JSON path. Not covered yet: a `file` secret whose path is checked at run time only (by the script, mode `0600` or stricter).
- Options reach a script as `--<name> <value>` (booleans and numbers as their text); a secret `{ "file": … }` as `--<name>-file <path>`; a secret `{ "env": "VAR" }` through the script's own `EASY_CS_AI_<COMPONENT>_<OPTION>` variable, set from `VAR` (exit 2 when `VAR` is not set), so it never appears on a command line; `{ "generate": true }` passes nothing.
- A requirement that is neither installed nor listed is checked before the first install, so nothing is installed by a run that cannot finish.
- `--prune` removes the models of the engines listed in the file that the file does not name, then every installed component the file does not list, in `uninstall --all` order.

## Definition of done

- `bats` tests in `EASY_CS_AI_ROOT` mode with fake components: each validation error with its JSON path, order from `requires`, missing requirement, re-run is a no-op, changed options reconfigure, defaults, model resolution (single engine, `default`, ambiguous), `force`, stdin input, `--dry-run`, failure at each step and resume, `--prune` (and its absence), the secret forms.
- Integration test on a fresh VM: `apply` of a configuration, `status` healthy, second `apply` changes nothing, `apply --prune` with a reduced file.
- `bats` tests of the `vm` field: `wrong_type` and `invalid_value` on its shape, `missing_vm`, the same component on two VMs accepted and twice on one VM refused, `several_defaults` per VM, a requirement satisfied by another VM refused, the four rows of [Where a model goes](#where-a-model-goes) (`vm` and `engine` given, `vm` only, `engine` only, neither) for the place they give and for `ambiguous_engine`, `engine_other_vm` and `unresolved_engine`, `unknown_vm` (also on a model of a one-VM file), the same model on two places accepted and on one place `duplicate_model`, the slice of a model (without `vm`, `engine` filled in when it was absent), a model's default chat interface (its VM's, else none) and `chat_interface_other_vm`, the slices (each without `vm`, models with their engine, order of first appearance, paths of the file as written), `apply` refused without `--vm`, `--vm` with an unknown name or on a file with no `vm`, `apply --vm` applying one slice, and a file with no `vm` unchanged.
- `shellcheck` clean.

## Open questions

- **Literal secrets in the file.** Answer: forbidden, see [spec: machine interface](spec-capabilities.md#secrets). The file is embedded in the generated VM script, so a literal would sit in the script and, on CloudStack, in the user-data, which is not confidential (see [contract](spec-script-contract.md#secrets)). Options: forbid literals (only `file`, `env`, `generate`), or allow them with a `WARN`. Same question as in [spec: VM script generator](spec-vm-generator.md#open-questions), to be settled together.
- **Several instances of one component** (e.g. two engines with different ports) are not expressible on one machine while the state has one entry per component. On different VMs they are, with `vm` ([Several VMs](#several-vms)).
- **Format version for `vm`.** The field is added without a bump of `schema_version` ([compatibility](#compatibility-of-the-vm-field)). A bump to 2 only when a file uses `vm` would give a CLI that does not know it a clear version error; to reconsider if configurations circulate across CLI versions.
- **Schema evolution**: how a new `schema_version` is migrated, once a second version exists.

# Spec: several VMs, and the editor of the configuration

[← Back to docs](README.md)

**Status:** proposed, being reworked. **Format version 2 is decided and not implemented**: a configuration is a list of `vms` that hold their components, the models are at the root and name their engine and their chat interface (see [spec: config](spec-config.md)), and there is no `links` any more: **the link between two VMs is carried by the model** (a model whose chat interface is on another VM than its engine). This spec generalizes the former "two VMs, the engine and the web interface apart" to **any number of VMs**, makes the session (the `config edit` command) a **creator and editor** of the configuration, apart from the generation of the scripts (the `script` command, see [spec: CLI](spec-cli.md#config-the-session)), and drops the special case of two VMs (the project is in development: nothing is kept for backward compatibility, neither with it nor with the flat file and the `links` of version 1). What the code **does today** (version 1: the `vm` field, the slices, the place of a model, `apply --vm`, `config validate --vm`, `links`) is to be rewritten for version 2. What was **implemented and does not depend on the format**: what a model needs, the proposal of a proxy ([journey, step 4](spec-journey.md#4-models)), the pass per VM, one script per VM with the `VM:` header, the `scripts` and `next_steps` of the JSON documents, the warnings of the validation, the declared resources of [spec: model fit](spec-model-fit.md), `proxy nginx list-upstreams`, the addresses of the self-signed certificate and `certificate_names`, and `chat-interface librechat add-endpoint` with a key and a certificate. **To do**: the format 2 in the validation, the slices and `apply`; the role and the name asked first for every VM, the first included (see [creating](#creating)); the roles and the free number of VMs in the session; the question of where the models are shown; the editor (`config edit <file>`); the next steps and warnings computed per model; and the rewrite of the tests and of the integration scenario that assumed two VMs.

## Purpose

Today a stack lives on **one machine** by default: the engine, the proxy and the chat interface share it, and the chat interface reaches the engine on the loopback (see [decision: LibreChat install](decision-librechat-install.md#4-reaching-the-models-from-the-container)). An administrator may want the inference engine on one VM (often the costly one, with a GPU), the web interface on another, small one, a second web interface for another team, a proxy alone, or any other split.

This spec lets one [configuration](spec-config.md) describe **any number of VMs**, lets the [generator](spec-vm-generator.md) **create and edit** it (`config edit`), then produce **one script per VM** from it (`script`), and says what the administrator does once the VMs are running. It adds no deployment model: each VM is a stack like today's, and the link between a chat interface and an engine of another VM is made by hand afterwards.

Adding a VM is part of the [journey](spec-journey.md) like any other decision: a person is asked in the session whether to add another VM after each one, and where the models of each engine VM are shown; a program writes the VMs, their components and the models with their engine and chat interface in the configuration, and both end on the same file. A configuration that exists can be **opened again** in the same session ([the editor](#editing)), to add a VM or change one.

## Principles

1. **A stack on one machine stays as it is.** The question of another VM defaults to "n", and the answers that give a one-VM script today give the same **slice** (what the VM embeds and installs), byte for byte, **apart from the changes below**; what a session writes around it changes (the file is a list of VMs, so a one-VM stack is a list of one VM, and the script file and its `VM:` header carry the name of the VM, see the last row). Nothing in **this spec** changes the loopback link, the `add` orchestration, the exit codes or the JSON of the one-VM case; the JSON changes only through the last two rows, which come from the specs this one relies on. There is **no other special case**: two VMs are the case N = 2 of the rules below, with no answer, name, text or link of their own. What a one-VM user sees change is this inventory, the only one of this spec (see also [what does not change](#what-does-not-change)):

   | Change | Comes from | Effect on one VM |
   | --- | --- | --- |
   | The question of another VM | this spec, see [creating](#creating) | A file of scripted answers needs one more line at the end of the session (an empty one takes the default `n`) |
   | The proposal of a proxy | the journey ([step 4](spec-journey.md#4-models)) | Only in a session that names a model on an engine that is not `protected` with no proxy on its VM (an engine alone, for instance): one more line at that place (an empty one takes its default `y`), and the script gains the proxy when it is accepted |
   | The sizing text, and a recommendation with no model | [spec: model fit](spec-model-fit.md#declared-resources) | The text of the recommended VM in the summary changes (the figures are those of the [shipped components](spec-model-fit.md#values-of-the-shipped-components)), and a session that names no model gets a recommendation, with the warning that the models come on top when the stack has an engine ([a stack with no model](spec-model-fit.md#a-stack-with-no-model)). The script and the configuration are not concerned |
   | The refusal of a model that cannot finish | [spec: config](spec-config.md#what-a-model-needs) | A file whose model needs a proxy or a provisioning component it does not give is refused by `config validate` and `script` (exit 2), where `apply` kept exit 4 at the model step (it still does); what a session does is in the [same section](spec-config.md#what-a-model-needs) |
   | The `models_not_checked` warning | [spec: model fit](spec-model-fit.md#llmfit-is-optional) | Built by the validation instead of the session's summary: a file with a model written with `force` and no provisioning component gains a `warnings` entry (with its `code`) in `config validate --json` and `script --json`. The text of the warning and the summary of a session do not change |
   | The role and the name of the first VM, and the form of the file | this spec, see [creating](#creating) | A session starts with two more questions (the role, then the name; an empty line takes each default), and the pass of the first VM is the one of its role, so the `custom` pass asks a type at a time like the later VMs, **with every type pre-selected** (default `y`). **A file always names its VMs, even for one machine** ([spec: config](spec-config.md#format)): a stack is mostly several VMs in practice, so one way of writing the file avoids a special case in the session, in the editor and in the validation. `script` writes `<output>-<vm>.<extension>` with the header `VM: <name> (1 of 1)`, and a file with one VM needs no `--vm` for `apply`. The slice that the VM receives is the same configuration as a stack of one VM, so what it installs does not change |
2. **One configuration, in two parts.** The `vms` hold the components of each machine, and the `models` at the root say, for each model, the engine it is installed on and the chat interface that shows it, as [component references](spec-config.md#component-references) (a VM and, when it is needed, the name of the component). The generator cuts the file into one **slice** per VM, a file of the same format with one VM; each script embeds only its slice. A VM, and `apply` running on it, never see that another VM exists. `schema_version` is 2.
3. **The link is finished by the administrator, once the VMs are up.** The address of an engine VM and its API key do not exist when the scripts are generated, so nothing about them goes into a script. The configuration says **which chat interface shows which model** (the `chat_interfaces` of the model: on the VM of its engine, the wiring of `add`; on another VM, the link between two machines); the generator tells the administrator what is left to do for the second case (see [Next steps](#next-steps)).
4. **No secret travels through a generated script.** The API key is generated on the engine VM, as today (see [Secrets](spec-script-contract.md#secrets)), and read from there on demand with `component proxy nginx show-key`.
5. **Roles help, they never bind.** The session offers [roles](#roles) as shortcuts, and works as well with none. A role is never written in the file and never a rule of the format.

## Roles

A **role** is an aid of the session: it restricts the types a pass asks and proposes what usually goes with them. A person never has to know in advance what a VM will hold: the `custom` role builds it one component at a time. It is **never stored** in the file (like the target specs of the models step, an early opinion), **never required**, and the VM of a file is judged by what it holds, not by a role.

| Role | Types the pass asks | What it adds |
| --- | --- | --- |
| `engine` | `provisioning`, `proxy`, `engine` | The pass must select an engine, and the proxy is proposed even with no model (the VMs that reach the engine do so through it) |
| `web` | `proxy`, `chat-interface` | The pass must select a chat interface |
| `custom` (default) | Every type, **one at a time**: for each, `Add <a|an> <type> on <vm>? (y/n) [y]` (the article agrees with the word: `an engine`) (**everything pre-selected**, for the first VM as for the others: an empty line at each question gives the full stack, rank 1 of each type; `n` removes a type), and on `y` the choice of the component (rank 1 preselected) and its options, before the next type | Nothing is imposed except that the VM ends with a component (otherwise the walk starts again with a message; a person who answers `n` everywhere meets it). The [dependencies](spec-journey.md#2-components-and-dependencies) and the [proxy proposal](spec-journey.md#4-models) are made as in a one-VM session |

- What `engine` and `web` typically hold: `llmfit`, `nginx`, `ollama` (or `vllm`) and the models on an engine VM; `nginx`, `librechat` on a web VM, which comes up with **no model of its own**, its selector empty until the models of an engine VM are linked to it. This is a convention of the session, **not a rule of the format**: any component may be given any VM, and the validation checks each slice as it checks a file of one VM. The rules about the models and their chat interface are in [spec: config](spec-config.md#component-references) and in [Validation](#validation).
- **Every VM has a name**, asked when the VM is added (default: its role, made unique by a number: `engine`, `web`, `web-2`, `vm-3` for `custom`); names have the shape of [spec: config](spec-config.md#vms). A name of the wrong shape, or already taken by another VM (`duplicate_vm`), is refused with the reason (and the VM that has the name) and asked again; nothing changes until the name is valid, at creation, in `a` and in `n <vm>`. The first VM is asked its role and its name like the others (default `custom`, `vm-1`), see [creating](#creating). A VM holds at least one component (`empty_vm` otherwise): with `engine` or `web` the component that defines the role is required and `none` for it is refused and asked again ([journey, step 2](spec-journey.md#2-components-and-dependencies)); with `custom` nothing is required except that the VM ends with a component. So a `custom` VM may hold an engine and a chat interface (a stack like a one-VM one, whose models are shown on the same VM), a second engine, or anything a file written by hand allows.
- Because `custom` imposes no proxy, the session proposes it **when a model is named** on an engine that is not `protected` and has none on its VM ([journey, step 4](spec-journey.md#4-models)); an engine VM with no model needs none and is valid, its models and its proxy may come later. In a pass of role `engine` the proxy is proposed even with no model, since the chat interfaces of the other VMs reach the engine through it. A refusal is allowed in a `custom` pass (the models of that engine are taken out, as in a one-VM session) and goes back to the components in a pass of role `engine`.
- The engine stays on its loopback and the proxy exposes it, as `add` already does for any engine that is not `protected` (none of the shipped ones is). The proxy is therefore **required** on an engine VM as soon as it holds a model, see [what a model needs](spec-config.md#what-a-model-needs). Nothing new on the engine side: its slice is the configuration an administrator who wants an API-only VM writes today. A model whose chat interface is on **another VM** is not wired by `add` on that VM: it is the link of the [next steps](#next-steps), made by hand.
- LibreChat `requires` nginx (for its web site), not an engine, so a slice with a chat interface and no engine validates and installs on its own.
- Several VMs may carry an nginx, each with its own options (server name, certificate strategy, ports): that is why each VM lists its own components.
- There is no limit to the number of VMs, in the session, the format or the generator.

## Validation

The validation of [spec: config](spec-config.md#validation) applies, with the file cut into slices; its errors for the VMs, the components and the [component references](spec-config.md#component-references) (`duplicate_vm`, `empty_vm`, `unknown_vm`, `unresolved_engine`, `unresolved_chat_interface`, `ambiguous_*`, `unsupported_count`, `duplicate_model`…) are listed there. The cases that a version 1 file had to express with `links` (`unlinked_vm`, `link_to_self`, `link_without_*`, `link_cycle`, `link_protected_engine`, `engine_unreachable`) **no longer exist**: the link is a model's chat interface, so a VM that no model refers to is simply a VM, an engine and a chat interface on the same VM is the normal case, and a proxy is required by the models that need it, not by an engine alone ([what a model needs](spec-config.md#what-a-model-needs)). This spec adds one **error** and one **warning**, shown by `config validate`, by the summary of the session, and by `script`; the warning does not change the exit code. A **steps model** is a model whose chat interface is on **another VM** than its engine, whose engine is not `protected` (the [next steps](#next-steps) are given for these):

| Code | Kind | When | Message (in substance) |
| --- | --- | --- | --- |
| `duplicate_server_name` | **error** (exit 2) | Two VMs write the **same** `server-name` (compared without regard to case) in the options of their proxy component | Two machines cannot answer to the same name: the second VM's `server-name` is a copy of the first one's. Give each VM its own name, or leave it out |
| `engine_address_unknown` | warning | The VM of the engine of a steps model has a proxy whose `server-name` option is **not written in the file**, and its effective `tls` is `self-signed` (the default; `letsencrypt` already needs an explicit `server-name`, and a `provided` certificate is the customer's) | The address of the engine VM is not known yet: its proxy will take the host name of the machine as its server name, and a self-signed certificate will also cover the addresses the machine has when it is installed. The VM that shows the models must reach the engine VM by one of those names or addresses. If none does, re-run `install proxy nginx` on the engine VM with the options it was installed with and `--server-name <name or address>` (an option left out returns to its default), before linking the models |

The warning exists because the address of a VM is usually not known when its script is generated (it is given by the cloud when the VM is created), so the session cannot ask for it and must not leave the administrator to find the problem at step 4. It states the situation and what covers it ([the certificate](#the-certificate-of-the-engine-vm)) **before** anything is created, and the fix (the re-run) is also in the [next steps](#next-steps). A `server-name` written in the file, a name or an address, removes the warning, and so does a `tls` that is not `self-signed`. A model with a chat interface **on its own VM** (the single machine) or with none never gives it: nothing reaches that engine from outside.

Each error has the shape of the other errors and the warning that of the other warnings of [spec: capabilities](spec-capabilities.md#config-validate), each with a `code` and the `vm` it is about. Both are computed on the whole file, so a validation of one slice gives neither.

`duplicate_server_name` is judged on what is **written** in the file, like `engine_address_unknown`: a `server-name` left to its default (the host name of each machine) is never compared. It concerns the `server-name` option of components of type `proxy`; it is at the path of the second option, names both VMs, and is not given by a validation of one slice.

**Where the session shows it.** The warning is about the models of one VM shown on another, so it can only be computed once the VMs and the models exist: a pass cannot give it. The **summary of the whole configuration** ([creating](#creating), [editing](#editing)) lists the errors and warnings that **need several VMs to be computed** (today `duplicate_server_name` and `engine_address_unknown`), each naming its `vm`. Every other warning (the `warn` of an option, `models_not_checked`) is judged inside one VM and shown **once**, in the summary of the pass of that VM, and not repeated in the summary of the whole configuration. `engine_address_unknown` can come from any session, since the address does not exist yet: it is not blocking and its text says the fix.

## In the session

The session is the [journey](spec-journey.md) walked once per VM. It writes one configuration: the VMs with their components, and the models with their engine and their chat interface. It **creates** a configuration, or **edits** one that exists.

### Creating

The session starts with the **first VM** like any other: **role and name first, for every VM**, with defaults (role `custom`, name made unique from the role: `vm-1` for the first one), then the pass of its role, the steps 2 to 5 and the summary of the VM. There is no question about a number of VMs; the question of another VM comes after each VM. The first VM is not a special case (no pass of its own, no name asked later): what a person learns on the first VM holds for the next ones, and the [editor](#editing) asks the same two questions in the same order for `a`. *Changed after a test of the session: the first VM used to be built as a one-VM stack, named only when another VM was added, with a pass of its own (every type at once, rank 1 pre-selected) that did not look like the passes that followed.*

- After the confirmation (`y`) of the summary of a VM, the session asks, when the package ships at least one engine and one chat interface (otherwise it is not asked):

  ```text
  Add another VM? (y/n) [n]
  ```

  Answered `n` (the default) with one VM, the session ends with a file of that one VM ([principle 1](#principles)); when that VM holds an engine with at least one model **and** a chat interface, the session asks a **confirmation** before writing the link, never linking them silently: `Show the models of <vm> in the chat interface <name> of <vm>? (y/n) [y]` (the same question as [where the models are shown](#where-the-models-are-shown), with one VM and one chat interface, so it is a yes or no). `y` writes `chat_interfaces: [ { "vm": "<vm>" } ]` on each model of the VM (the wiring of `add` on one machine), `n` writes no `chat_interfaces` on them (the engine is then used through its API). The file is **explicit** either way. A VM with no chat interface, or with an engine and no model, gets no question. The effect on the scripted answers of the tests and of the [parity scenarios](../tests/unit/parity/README.md) is in [principle 1](#principles).
- Answered `y`, the session builds the next VM: its [role](#roles) (`engine`, `web` or `custom`, default `custom`), its **name**, and a pass, which is the session as it is today restricted to the types of the role. Every component written goes in the `components` of the VM of its pass, and every model asked in that pass is written at the root with the engine of that VM as its `engine` reference ([component references](spec-config.md#component-references)). Each pass ends on its own [summary](spec-journey.md#5-validate-show-confirm) (components in install order, options, models, platforms, warnings, and the recommended VM of the pass when it is computed), with the same confirm / redo (`c`, `o`, `m`) / cancel, and then the question of another VM again, so a stack of any size is built one VM at a time. Cancelling at any point cancels everything: nothing is written, exit 0.
- **The models step belongs to every pass that selected an engine**, with the same two orders and the same sizing; `m` is offered only in such a pass. The [proposal of a proxy](spec-journey.md#4-models) is made in every pass of role `engine` (with or without a model) and, for the other roles, only when it names a model on an engine that is not `protected` with no proxy on its VM. A refusal in a pass of role `engine` goes back to the components of that pass.
- The recommended VM of each pass comes from `provisioning llmfit plan`, called with the components **of that VM** (`--component` for each), so an engine VM carries no share for an interface that is not on it. A pass with models, named in the `m` order ([choosing models](spec-model-fit.md#choosing-models-in-a-session); in the `h` order the VM is imposed and there is no recommendation for models), adds them, each as `<model>@<engine>` with the engine of its [place](spec-config.md#component-references), and a pass that ends with no model is sized as [a stack with no model](spec-model-fit.md#a-stack-with-no-model) (the cores of the `h` order belong to the VM they were given for, see [choosing models](spec-model-fit.md#choosing-models-in-a-session)). How `plan` counts the models of an engine VM is in [models loaded together](spec-model-fit.md#models-loaded-together).
- <a id="where-the-models-are-shown"></a>**When the answer to "another VM" is `n` and there are several VMs**, the session asks **where the models are shown**. For every VM that holds an engine **and at least one model**, in the order of the file:

  ```text
  Which chat interface shows the models of <engine_vm>? (a VM with a chat interface, none) [<default>]
  ```

  The question is preceded, **once** per session, by a sentence that says what it decides: *a model is installed on an engine and shown in a chat interface; when the chat interface is on another VM, the two machines are linked by hand once they are up, the steps are printed.* The answer is a VM that holds a chat interface (when that VM holds several, the question names them and asks which one: nothing is guessed), or `none`: **it is written on each model of the engine VM** as its `chat_interfaces`, so the file says it model by model (a person who wants another chat interface for one model uses `m <vm>` in the [editor](#editing)). The format allows several, the validation one for now (`unsupported_count`, [spec: config](spec-config.md#models)). The default is the engine VM itself when it holds a chat interface (the wiring of `add` on one machine), else the only VM that holds one, else `none`. An answer naming a VM with no chat interface is refused with the reason and asked again. The question is always asked, with one VM as with several (with one VM it is the confirmation above): nothing is shown anywhere silently ([rule 3 of the journey](spec-journey.md#rules)), and one Enter takes the usual answer. Every place that shows the result writes it with its meaning, not as a bare arrow: `llama3.2:3b on gpu, shown in web` (a model with no chat interface: `shown nowhere`), so that the direction is read, not guessed.
- The session then shows the **summary of the whole configuration**, the one of the [editor](#editing): VMs, components, models (each with its engine and where it is shown) and **every warning**, with the editor's commands. Nothing is written while an error stands: the person edits it (`e`), changes where the models are shown (`l`) or removes it (`r`). `y` writes the configuration (and no script: `script` generates them from the file, and the session says so); cancel and the end of input write nothing, exit 0.
- The session asks no [package source](spec-vm-generator.md#package-source): it writes no script. `script` takes it from its options, the same for every script.

### Editing

```text
config edit <file>
```

Opens an existing configuration in the same session. **Saving writes the configuration and nothing else**: the scripts are not regenerated (that is `script <file>`, which the editor names when it has saved), so the scripts on disk may describe an older configuration than the file until it is run. The file is written where the session [asks it](#the-file-written), by default back to itself.

- **Loading.** The file is read and validated like `config validate --target fresh`. A file that is not JSON, or cannot be read, and a missing file are exit 2 (a creation is `config edit` with no file). A file with validation errors **opens anyway** (fixing it is what the editor is for): the errors are shown in the summary, numbered, each with its path, its code and the command that fixes it, and **nothing is written while one remains**.
- **The summary of the whole configuration** is the first screen: VMs in order, with their components, options (secrets masked), platforms, then the models, each with its engine and where it is shown, and **every warning**. A VM shows `models:` only if it has an engine: `models: none` on a VM that holds no engine (a chat interface and a proxy) means nothing and is not printed, in this summary as in the summary of a pass. Its prompt:

  ```text
  a add a VM   e <vm> edit   m <vm> models   l where models are shown   n <vm> rename   r <vm> remove   f fix   y write   q quit
  ```

- `a` adds a VM: its role (optional, `custom` by default) and its name, then its pass, then **where models are shown**: the question of [creating](#where-the-models-are-shown) for the new VM when it holds models and, when the new VM holds a chat interface, for each engine VM whose models are shown nowhere (default: the new VM), so that the person finds the question at the place it matters, and not only in `l`. The prompt line has a one-line help for each command (`?` prints it): `e` edit a VM's components and options, `m` its models (and, model by model, the chat interface that shows each one), `l` which chat interface shows the models of each engine VM, and so on. `e <vm>` redoes the pass of an existing VM **from its current content** (components preselected, options and models offered as defaults, as the specs of the models step are offered again when it is redone); it never imposes a role, the VM is edited as `custom`. `m <vm>` redoes its models only. `l` redoes the question of where the models are shown (each engine VM, as in creating, with the current answer as default). `n <vm>` renames a VM in its components and in the references of the models that name it. `r <vm>` removes a VM with its components and the models installed on its engine, and empties the `chat_interfaces` of the models that were shown in its chat interface (they stay, shown nowhere), after telling what goes. **Removing a component that others depend on** (the engine of models, the chat interface that shows models) in `e <vm>` is announced first, listing what depends on it, and the person chooses: `Remove them too? (y/n) [y]`. `y` removes the dependents in cascade (the models of that engine; for a chat interface, the references to it in the models, which stay shown nowhere); `n` removes only the component and leaves the errors that follow (`unresolved_engine`, `unresolved_chat_interface`…), which `f` then proposes to fix. Nothing is removed without having been announced.
- **Fixing errors.** The editor is where errors are corrected, whatever their origin (a file written by hand, a program, a change just made in the editor). `f` walks the errors one at a time and **re-asks the question of the field at the path of the error** ([rule 2 of the journey](spec-journey.md#rules): every field has a question): an option outside its values asks that option again with its default, a `missing_requirement` proposes the component that is missing (`Add <proxy>? (y/n)`, then its options), a model that resolves to no engine (`unresolved_engine`, `ambiguous_engine`, `unknown_vm`) asks its engine again, one whose chat interface does not resolve asks where it is shown again, an array of more than one reference (`unsupported_count`) asks which one to keep. The cases with no question to re-ask are proposed as a choice: `duplicate_server_name` re-asks the `server-name` option of the second VM; a VM with no component (`empty_vm`) or a component twice (`duplicate_component`) offers to edit (`e <vm>`) or to remove it (`r`); an entry the CLI does not know (`unknown_key`, `unknown_component`, `unknown_option`) offers to remove it. Each fix is validated at once and the list is shown again, so a person goes from the first error to `ok` without writing any JSON. A change that creates an error does the same: the removal of a VM, of a component or of a model, and a rename, list what is left unresolved and offer to fix each.
- **A file written by hand** opens as it is: there is no other form, so there is nothing to convert. A file of version 1 (a flat file, a `vm` field, `links`) is refused at loading with `unsupported_schema_version`, exit 2 ([spec: config](spec-config.md#compatibility)); the editor does not open it.
- **The editor never drops what it does not show.** The session offers one component per type per VM, and no free `name` for a component; entries it does not present (a second component of a type on a VM, a free `name`, an option it has no question for, a model with several references where the validation will allow them) are kept as they are, and so is a `default` it does not touch.
- <a id="the-file-written"></a>**The file written.** After `y` (and for a creation as for an edit), the session asks where to write, with a default, before anything is written:

  ```text
  File to write (overwritten, or created if it does not exist) [./easy-cs-ai.json]:
  ```

  The default is the file opened by `config edit <file>`, or `./easy-cs-ai.json` for a creation; Enter takes it. Any other name is accepted: the person makes a copy of the file being edited, or creates the file elsewhere. A name that is an existing file **other than the one opened** is confirmed first (`<file> exists. Overwrite? (y/n) [n]`; `n` asks the name again), so that the default never hides an overwrite and another name never silently destroys a file. A name in a directory that does not exist or is not writable is refused with the reason and asked again. This replaces any `--output` option for `config edit`. The end of input at this question is a cancel: nothing is written.
- **Writing.** `y` first checks that the file to be edited has **not changed since it was opened** (the content read at opening is compared with the file on disk, for a change made in another terminal or by git): if it has, nothing is written, and the editor says so and leaves the choice to the person (`q`, then open the file again: the editor never overwrites a file changed by someone else). Then it validates again, asks [the file](#the-file-written) and writes the configuration there: a temporary file in the same directory, then rename, the mode kept when the file existed, so that the file is whole or unchanged. It then names the command that makes the scripts (`easy-cs-ai script <file>`). With `--dry-run` the result goes to stderr and nothing is written. `q`, cancel or the end of input leave the file untouched, exit 0.
- **Scripts left behind.** Because saving regenerates nothing, the scripts of a removed or renamed VM are still there, and so are those of the others, with their old content. `script` is the one that [lists the stale scripts](spec-vm-generator.md#script-file) after writing; the editor deletes nothing and writes none.
- The editor changes nothing on the machine and needs no root, like the rest of the generator.

### What is written

| Command | What it writes |
| --- | --- |
| `config edit` (creation) | `./easy-cs-ai.json` by default, the name asked: **one file**, the VMs with their components and the models |
| `config edit <file>` (editing) | the file by default, the name asked |
| `script <file>` | `./easy-cs-ai-vm-<name>.sh`, one per VM (a single VM too), written together |

- With `--output <path>` (`script` only): the VM name is inserted before the extension of each script: `--output vm.sh` gives `vm-engine.sh` and `vm-web.sh`.
- The scripts are written together: if one cannot be written, none is kept.
- `--dry-run` runs the whole session (`config edit`) or the generation (`script`) and prints every result to stderr.
- The header of each script gains one line, `VM: <name> (<rank> of <N>)`, so that a script found on a VM says which side of a set it is (`VM: a (1 of 1)` for a file of one VM).
- The size warning (32 KB) applies to each script.

## For a program

The same file, written in one go: a program (or an agent working for a person) writes the configuration with its `vms` and its `models` (the `engine` and the `chat_interfaces` of each), validates it with `config validate <file> --target fresh` (which cuts it into slices and checks each; the default target `this` is one machine and needs `--vm` when the file has several VMs, see [spec: capabilities](spec-capabilities.md#config-validate)), then runs `script <file>`, which gives the same scripts the session's file does. A program that **edits** a file edits the JSON and validates it again: the [editor](#editing) is its rendering for a person. There is no other path and no other flag: the answers to the VM question and to the question of where the models are shown **are** the `vms` and the `chat_interfaces` of the models, so that [rule 2 of the journey](spec-journey.md#rules) holds without exception, and `config schema` lists the fields. The role is an early opinion and has no field.

The documents of `script --json` and `config validate --json` for several VMs (`scripts`, the resolved places and chat interfaces in `plan`, `next_steps`, the warnings, what a validation of one slice gives) are defined in [spec: capabilities](spec-capabilities.md#commands) and [`config validate`](spec-capabilities.md#config-validate); the content of `next_steps` is [below](#next-steps).

The journey text of [`guide.txt`](../install_scripts/guide.txt) tells an agent to ask the user which VMs the stack is made of, to give each VM its components, to say for each model its engine and the chat interface that shows it, and to edit a file by validating it again; a test checks that it names the same commands as the next steps.

## Next steps

When the file has **at least one steps model** (a model whose chat interface is on another VM than its engine, see [Validation](#validation)), the validation computes the list of what remains for the administrator (see [Where they are computed](#where-they-are-computed)). After the scripts are written, `script` prints it on stderr (not asked to confirm), and with `--json` it is the array `next_steps`. One rule for every number of VMs and of models, with no text of its own for two VMs:

- **Step 1** is always there: "Run each script as root on its VM, the engine VMs first." when there is at least one steps model (the order only matters for the models described below), else "Run each script as root on its VM." A file with no steps model gives step 1 alone, in its second wording.
- For each **engine VM** that holds at least one steps model (in the order of the file): **step 2**, read the API key, the URL of each model and the names and addresses its certificate covers; and **step 3**, let the VMs that show its models reach it on the HTTPS port of its proxy (443 unless you set `--port`): firewall, security group.
- For each **pair** of an engine VM and a chat-interface VM that shows at least one of its models: **step 4**, link each of those models from the VM that holds the chat interface, with `add-endpoint` (one command per model).
- A model whose chat interface is on **its own VM** is wired by `add` and gives no step; a model with **no** chat interface gives none either, and a VM that holds no model gives none: its models may come later, and are linked by hand with the `add-endpoint` of the contract. A model of a `protected` engine shown on another VM is not a steps model: no shipped engine is protected, and how such an engine publishes its URL and its key is an [open question](#open-questions), so that the steps never give a command that cannot work.

For a person the text is the following, here for a model of the VM `engine` shown in the VM `web` ([who writes which lines](#rules-for-the-text)):

```text
2 scripts written, one per VM:
  ./easy-cs-ai-vm-engine.sh   VM engine  (<the components of that VM>)
  ./easy-cs-ai-vm-web.sh   VM web  (<the components of that VM>)

What is left to do once the VMs are up:
  1. Run each script as root on its VM, the engine VMs first.
  2. On the engine VM engine, read the API key, the URL of each model and the
     names and addresses its certificate covers:
       sudo easy-cs-ai component proxy nginx show-key
       easy-cs-ai component proxy nginx list-upstreams
       easy-cs-ai component proxy nginx status          (certificate_names)
  3. Let the VM web reach the VM engine on the HTTPS port of its proxy
     (443 unless you set --port): firewall, security group.
  4. On the VM web, link each model of the VM engine:
       sudo easy-cs-ai component chat-interface librechat add-endpoint <engine>-<model> <url> \
         --model <model> --api-key-file <file>
     <url> is the one read in step 2, <file> holds the key (mode 0600, or - for
     stdin), and the endpoint name is suggested unique on the VM (a chat
     interface may link several engine VMs).
     With the default self-signed certificate, copy the certificate of the
     engine VM (/etc/easy-cs-ai/nginx/server.crt) to the VM web and add
     --ca-file <file>. The host in <url> must be one the certificate covers
     (certificate_names, step 2): the server name printed by list-upstreams,
     or, when no server name was given, an address of the engine VM, which
     you put in place of the host. If the VM web can reach neither, or the
     address changed since the proxy was installed, re-run on the engine VM
       sudo easy-cs-ai install proxy nginx <the options it was installed with> \
         --server-name <name or address>
     (an option left out returns to its default) which renews a self-signed
     certificate (copy it again), then read step 2 again.
Until step 4 is done, the model list of the chat interface stays empty.
```

With several steps models the steps are numbered in order, and there is one step 2 and one step 3 per engine VM and one step 4 per pair of engine VM and chat-interface VM, each naming its VMs. With a single step (no steps model), the person's text is the title and `  1. Run each script as root on its VM.`, with no closing line, and `next_steps` is `[ "Run each script as root on its VM." ]`.

Rules for the text:

- **Fixed text, filled with what the configuration says.** The component names, the VM names and the models are those of the file (one `add-endpoint` line per model, with its `--model`). The address, the port, the URL and the files stay placeholders: they do not exist yet.
- **The text is the validation's, the commands are the contract's.** It never invents an action or an option: a bats test checks that every action and option named in the text is in the `describe` of the script it names (`actions` of nginx, `action_options` of the LibreChat script, see [Contract additions](#contract-additions)). The list is given only by a package whose scripts have them, so the CLI never gives a command that fails.
- <a id="rules-for-the-text"></a>**Who writes which lines.** The heading (`<N> scripts written…` and the file of each VM) is the **generator's own**: it names the files it wrote, which the validation cannot know (`--output` changes them, and `config validate` writes nothing), and it is never part of `next_steps`. The steps are the validation's and what `next_steps` holds, **one string per step** (a step with commands is one multi-line string, with no numbering in it and no file name of a script: step 1 says "each script", not its path). The title `What is left to do once the VMs are up:`, the numbering and the closing line (when there are several steps) are added by the rendering of the validation, which `script` and `config validate` share, from the same array: what a person reads and the strings of `next_steps` are the same text in the same order.
- `config edit` produces no script: it prints one line naming the file written and the command that makes the scripts (`easy-cs-ai script <file>`) instead of the list. `config edit` has no `--json`, so this line is never in a `next_steps`.
- A file whose models are all shown on the VM of their engine (a stack on one machine, or on several machines that work apart) has step 1 alone: nothing is printed for the link, since there is none to make.

### Where they are computed

The list is computed by the validation of [spec: capabilities](spec-capabilities.md#config-validate), in the same place as the warnings, from the file (the `chat_interfaces` of its models included) and the `describe` of the shipped scripts: nothing of the machine, and no script written. The condition, the text and the models filled in are a rule of the capability, not of the generator ([rule 4](spec-journey.md#rules)), so improving them improves both ways at once: `script` computes nothing of the list, it prints its own heading, then the list after writing the scripts, and puts it in its `--json`; `config validate --json` returns it too, so a program can show it before generating. `guide.txt` carries the procedure for a reader that is a model. It is written by hand, not generated, and a test keeps it in step with the list (see [Definition of done](#definition-of-done)).

## Contract additions

Two actions change, and a detail of `install` and `status` of the nginx proxy is added (see [The certificate of the engine VM](#the-certificate-of-the-engine-vm)). The existing calls behave exactly as today.

### `proxy nginx list-upstreams`

```text
component proxy nginx list-upstreams
```

Prints the models the proxy fronts, each with the URL an external client uses, as a JSON array on stdout:

```json
[ { "name": "ollama-llama3.2-3b", "url": "https://llm.example.org/ollama-llama3.2-3b/v1" } ]
```

- The `url` is what `add-upstream` printed: the OpenAI base URL built from the server name and the port of the install (no port when it is 443). The state keeps the internal URL of the engine, which no other machine can use, so this action is how the administrator gets the URL to give to `add-endpoint`.
- Read-only: no root, no lock, not journaled, like `list-models`. `[]` when the proxy fronts nothing, exit 4 when it is not installed. It reads the state, so it answers whether the proxy is healthy or not.
- It never prints the API key: `show-key` stays the only action that prints a secret.
- It is an action of the type `proxy` ([contract](spec-script-contract.md#type-specific-actions)), declared in the `actions` of the `describe`, so another proxy component offers it too.

### `chat-interface librechat add-endpoint`

Calls without the new options behave exactly as today: `apiKey: "unused"`, the system trust store.

```text
component chat-interface librechat add-endpoint <name> <url> [--model <model>] [--api-key-file <path|->] [--ca-file <path>]
```

| Option | Meaning |
| --- | --- |
| `--api-key-file <path>` | The API key the endpoint expects. A file of mode `0600` or stricter, or `-` for stdin, never on the command line (see [Secrets](spec-script-contract.md#secrets)). Without it, the placeholder key of the local link |
| `--ca-file <path>` | PEM certificate (or CA) the endpoint is verified against, for an engine VM whose proxy uses a self-signed or private-CA certificate. Without it, the system trust store. Verification is never turned off |

- **The key is stored as a secret**: in a file of mode `0600` owned by root under `/etc/easy-cs-ai/secrets/`, referenced by the api container through its environment file, and **never written in `librechat.yaml`**, in the state, in the logs or in `--dry-run`. The path goes in the state `secrets`, the value nowhere. It is **kept by `uninstall` and removed only with `--purge`**, like the other secrets of LibreChat ([script contract](spec-script-contract.md#uninstall)); `remove-endpoint` removes it at once.
- **The certificate is public**: copied to `/etc/easy-cs-ai/librechat/`, mounted read-only in the api container and trusted there. The endpoints share one bundle, rebuilt from the certificates of all of them, since the container takes one file. The certificates and the bundle are recorded in the state `files` when they are written, so `uninstall` always removes them (and the `librechat/` directory with them when it is empty).
- The two options, and the existing `--model`, are declared under `action_options` of `add-endpoint` in `describe` (they are not options of the configuration), so a program can discover them. The [next steps](#next-steps) name `--model`, and the test that checks their commands against the `describe` needs it declared.
- Like today, the action recreates only the `api` container, and only when the rendered files changed. It is idempotent: the same arguments change nothing, a new key or certificate replaces the old one. `remove-endpoint` removes the entry, its key file and its share of the bundle.
- A remote endpoint is recorded in the state `endpoints` like a local one (`name`, `url`, `model`), with the key file in `secrets`.
- `easy-cs-ai add` never passes these options: it links models of an engine of the same machine. The remote link is made by hand, with the component action.
- **Checked on 2026-10-16** (LibreChat 0.8.7, the image pinned by digest): the key of a custom endpoint may be an environment variable reference in `librechat.yaml` (`apiKey: '${NAME}'`, which the LibreChat documentation recommends over a literal), and `NODE_EXTRA_CA_CERTS` is honoured by the Node of the image (v24.16.0): against a self-signed HTTPS server, `fetch`, the `axios` and the `openai` package of the image fail with `DEPTH_ZERO_SELF_SIGNED_CERT` without the variable and succeed with it, the `Authorization` header carrying the key. What is **not** covered is the whole path through LibreChat itself (the `api` container reading the key from its environment file and the bundle mounted read-only): the integration test on two VMs is where it is confirmed. If it fails there, the mechanism changes, not the options above.

### The certificate of the engine VM

Implemented. The address of the engine VM is usually not known when its script is generated, and a self-signed certificate is checked against the host of the URL the linked VM uses ([decision: certificates](decision-nginx-certificates.md#self-signed)). Two additions to `proxy nginx`, neither changing a call that gives a `--server-name`:

- **`install` with `--tls self-signed` and no `--server-name`** adds to the names the certificate covers the **addresses the machine has when the certificate is made**: every address of global scope (not loopback, not link-local), read from the system. The certificate then covers the host name (the default server name), `localhost`, `127.0.0.1` and those addresses, so the administrator can use the name or an address he reads on the VM, without knowing it beforehand. With an explicit `--server-name`, the certificate is what it is today (that name, `localhost`, `127.0.0.1`). `EASY_CS_AI_NGINX_ADDRESSES` (space separated) replaces the detection, for the tests, as `EASY_CS_AI_HOST_IDS` does for the platform.
- **A re-run does not remake the certificate for a new address.** The rule stays the one of the script today, "regenerated only when the certificate no longer covers the server name": a certificate that already covers it is kept, whether the name is the one of the first install or another one it already covers, since the linked VM holds a copy of it and a new one would break the link. An address that changes after the install (DHCP) is not covered: the fix is the re-run with `--server-name` **and the options the proxy was installed with**, since `install` takes an option left out from its default and not from the state (the [contract](spec-script-contract.md#parameters) precedence), which is the last lines of step 4 of the [next steps](#next-steps).
- **`status` of nginx gains `certificate_names`**: the array of the DNS names and addresses of the certificate nginx serves, read from the certificate itself (probed, not copied from the state), `[]` when it cannot be read. It is optional, additive and not a bump of `schema_version`; the other fields of `status` are unchanged. It is what step 2 reads, so the administrator knows which host the linked VM may use.
- `provided` and `letsencrypt` certificates are the customer's or Let's Encrypt's: `install` adds nothing to them, and `certificate_names` shows what they cover. Let's Encrypt needs an explicit `--server-name` already.

- Tests of `engine_address_unknown`, one case per condition of its [row](#validation): given when they all hold (`tls` written or by default); not given with a `server-name` written (a name, or an address), with `tls` `provided` or `letsencrypt`, for an engine VM with no model, for a `protected` engine, for a model shown on its own VM or nowhere, or by a validation of one slice; shown once, in the summary of the whole configuration; the same warning, with its `vm`, in `config validate --json` and in `script`; no change of exit code.
- `bats` tests of the certificate of the engine VM, in `EASY_CS_AI_ROOT` mode with `EASY_CS_AI_NGINX_ADDRESSES`: no `--server-name` and `--tls self-signed` gives a certificate that covers the host name, `localhost`, `127.0.0.1` and the addresses; an explicit `--server-name` gives the certificate of today (no address added); a re-run with a new address keeps the certificate, a re-run with another name makes a new one; `provided` is untouched; `status` has `certificate_names` read from the served certificate (and `[]` when it cannot be read), with no other field changed. The step 2 and 4 text names only actions and options that are in the `describe` of nginx (`status`, `install`, `--server-name`).
- `bats` tests of `list-upstreams` in `EASY_CS_AI_ROOT` mode: the public URL of each upstream (port 443 and another port, with the server name), `[]` when there is none, exit 4 when the proxy is not installed, no root needed, nothing journaled, the API key never printed, and the action listed in `actions` of `describe`.
- `bats` tests of `add-endpoint` in `EASY_CS_AI_ROOT` mode: without the new options the rendered files are identical to today's; with `--api-key-file` (file, stdin, too-open file refused with exit 2, never in `librechat.yaml`, state, logs or `--dry-run`); with `--ca-file` (copied, bundle rebuilt, an invalid PEM refused); idempotence; `remove-endpoint` removes the key and the certificate; `uninstall` of LibreChat with such an endpoint removes the certificate and the bundle and keeps the key file, and `uninstall --purge` removes the key too.
- Integration test on several VMs (`tests/integration/two-vm.sh` becomes `multi-vm.sh`, see [its README](../tests/integration/README.md)): an engine VM and two web VMs, all scripts run, the models shown on the web VMs linked as in the next steps, a message answered through the api container of each web VM, the scripts run a second time change nothing. The single-VM test stays as it is; two VMs are the case of one web VM, not a test of their own.
- `shellcheck` clean; `--help` of the generator and `guide` consistent with this spec.

## Open questions

- **Sizing of a VM.** Settled by [declared resources](spec-model-fit.md#declared-resources) and [a stack with no model](spec-model-fit.md#a-stack-with-no-model). What stays open is the quality of the figures, which is the calibration of the [estimated margin](spec-model-fit.md#open-questions), not something specific to this spec. The editor re-sizes a VM by listing its components again for `plan`; `plan --config <file> --vm <name>` would read them from the file and becomes worth having.
- **A command to finish the link.** `add-endpoint` by hand is the smallest thing. A higher-level command that reads the key and the certificate from the engine VM would be easier to use, and needs access from one VM to the other that the project does not assume.
- **The models listed by the endpoint.** With `--model`, LibreChat shows that model only (`fetch: false`). Without, it fetches the list of the engine, through the key and the TLS, which adds a network dependency at start. To settle with the first real test.
- **Which models a chat interface shows.** Settled by format 2: each model says where it is shown (`chat_interfaces`), so a chat interface shows the models that name it, not all those of an engine VM. The session asks once per engine VM and writes the answer on each of its models; showing different models of one engine in different chat interfaces is done model by model in the editor (`m <vm>`) or in the file.
- **A VM with no component.** A VM exists by its entry in `vms`, and `empty_vm` refuses one with no component, so a VM is never left in the file by accident; a VM kept to be filled later (a name, a note, later a size or an address) is not specified.
- **Errors with no fix in the editor.** An error that the editor cannot turn into a question or a choice (a file whose structure is not an object, for instance) is exit 2 at loading, with the message of the validation: the editor opens only what it can show.
- **Settled: the name of the entry.** The editor is `config edit <file>` and the creation `config edit` with no file, apart from `script`, so that the only interactive command is `config edit` (`config validate` and `config schema` never prompt, and the three are written the same way) and the scripts are never a side effect of a save.
- **Showing what an edit changes.** The editor shows the whole summary, not a difference with the file read. A `config diff` capability would serve the editor and a program alike.
- **The address of the engine VM and its certificate.** Settled by the [`engine_address_unknown` warning](#validation), the [addresses added to the self-signed certificate](#the-certificate-of-the-engine-vm) and the last lines of step 4. What stays open: an address that changes after the install is not covered (the re-run with `--server-name` and the same options is the answer, a certificate that follows the address would break the copy the linked VM holds), and a name that no DNS gives to the engine VM, for which the administrator must give an address.
- **Structured next steps.** `next_steps` is an array of strings, one per step, enough for an agent that reads them and for the text. If a program has to act on a step (find the `add-endpoint` command of a model), the entries would become objects (`id`, `vm`, `text`); documents of one VM are not concerned.
- **A `protected` engine whose models are shown on another VM.** No shipped engine is `protected`, and no step is given for it, so that nothing promises a link that cannot be made. Linking a chat interface to such an engine would need its URL and its key, which the [contract](spec-script-contract.md#describe) does not say how a `protected` engine publishes (a proxy action does not apply, since `add` does not front it). To specify with the first `protected` engine, with the error it then needs.
- **Several chat interfaces per model.** A model is one instance on **one engine** (`engine`, [spec: config](spec-config.md#models)): the same model on two engines is two entries. The format allows several chat interfaces to show it (`chat_interfaces`); the validation accepts at most one for now (`unsupported_count`), and the session writes one. What the next steps do with several (one `add-endpoint` per chat interface) is to specify when the limit is lifted.
- **The next steps in the header** of each script, so that a script found on a VM says what is left to do. Only the VM line is in this version.
